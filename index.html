Phase 1

Windows Domains

Understanding why centralized identity management exists and how Windows Domains solve the problems of decentralized user management.

💻

Workgroup Model

Each PC manages users locally. Same user must be created on every machine. Password changes must be updated everywhere. High admin overhead, security gaps, poor scalability.

🏢

Domain Model

One central system manages all users and access. Single sign-on across all machines. Centralized policy enforcement. Scalable to thousands of users and computers.

Workgroup vs Domain
WORKGROUP (Decentralized)
PC1 → Local Users
PC2 → Local Users
PC3 → Local Users
DOMAIN (Centralized)
Client Machines
    ↓
Domain Controller
    ↓
Centralized Authentication
Key Insight: A Windows Domain = centralized control boundary for an enterprise network. Instead of managing 500 users across 200 computers individually, one central directory handles everything.

Phase 2

AD Objects

Active Directory stores everything as objects — users, computers, groups, service accounts, and more. Each object represents a real entity in the organization.

👤

User Objects

People or services that need domain access

Security principals that can be authenticated and assigned permissions. Includes employee accounts, admin accounts, and service accounts.
💻

Computer Objects

Machines joined to the domain

Every domain-joined computer gets a machine account ending with $. Example: TOM-PC becomes TOM-PC$. These are also security principals.
👥

Security Groups

Collective permission management

Assign permissions to groups instead of individual users. Members inherit permissions automatically. Improves manageability and scalability.
⚙️

Service Accounts

Application & service identities

Special accounts used by applications (IIS, databases, backups). Not for regular login. Have limited privileges for specific automated tasks.
🖨️

Printers

Shared network resources

Network printers published in AD so users can discover and connect to them through the directory.
📁

Shared Resources

Files, folders, applications

Shared folders and applications registered in AD for centralized access control and discovery.

Users & Groups

Understanding security principals and how groups enable scalable permission management across the enterprise.

👤 Users
↓
👥 Security Groups
↓

User Types

  • Employee accounts — Normal domain users
  • Admin accounts — Privileged users (Domain Admins)
  • Service accounts — Application/service identities

Group-Based Permissions

Instead of granting access to each user individually, add users to a group and assign permissions to the group. All members inherit those permissions automatically.

Group: HR-Team
  Members: Alice, Bob, Charlie
  Permission: HR Folder Access
  → All members gain access automatically
🔑

Security Principals

Users are called "security principals" because they can be authenticated, assigned permissions, and access domain resources. Computer accounts are also security principals.

Organizational Units

OUs are the backbone of enterprise AD organization — they group users by department and enable policy application at scale.

Critical Concept: OUs are used to apply Group Policies to a specific set of users or computers. A user can belong to only ONE OU, but can belong to MULTIPLE groups.

Phase 5 — Critical

Delegation

Delegation allows limited administrative control without granting full Domain Admin rights — following the Principle of Least Privilege.

THM Question: The process of granting privileges to a user over some OU or other AD Object is called… Answer: Delegation
👑 Domain Admin
↓
🔓 Delegated Rights
↓
👤 Helpdesk User (Phillip)
↓
📂 Specific OU Management

Phillip — IT Support Scenario

Can do:

  • Reset passwords in Sales/Marketing/Management OUs
  • Unlock locked user accounts
  • Modify user attributes in delegated OUs

Cannot do:

  • ✗ Modify Domain Admin accounts
  • ✗ Change domain-wide policies
  • ✗ Manage Domain Controllers

Principle of Least Privilege

Users receive only the minimum permissions required. If Phillip's account is compromised, the attacker only gets limited OU-level control — not full domain compromise.

Security Warning: Delegation misconfigurations can create privilege escalation paths. Over-delegated users become attack vectors.
RoleAccess Scope
Domain AdminFull domain control — everything
Delegated Support UserLimited control on specific OUs only

Group Policy Basics

Group Policy (GPO) is the mechanism for centrally enforcing configuration settings across all domain users and computers.

↓
📝 Creates GPO
↓
📂 Stored in SYSVOL
↓
💻 Clients Retrieve Policy
↓
✅ Policy Applied
🎯

Centralized Enforcement

Configure once on the domain → automatically applied across all machines. No manual per-machine configuration needed.

🔧

Policy Types

Password complexity, software installation, desktop restrictions, security settings, and more.

📡

Automatic Application

Policies apply when users log in or computers start. Consistent enforcement across the entire domain.

Enterprise Impact: Without GPO, an admin would need to configure 500 machines manually. With GPO, configure once and it applies everywhere automatically.

Phase 8 — Critical

Kerberos Authentication

Kerberos is the default authentication protocol in modern Windows domains — using tickets instead of sending passwords repeatedly.

THM Question: When referring to Kerberos, what ticket allows requesting further tickets? Answer: Ticket Granting Ticket (TGT)
🔐 User Login
↓
🎫 TGT Issued (Master Ticket)
↓
🎟️ TGS Requested (Service Ticket)
↓
✅ Service Access Granted
TicketPurpose
TGT (Ticket Granting Ticket)Master authentication proof — "I am a valid domain user"
TGS (Ticket Granting Service)Service-specific access ticket — "Allow me to access this specific service"
1

Login Request

User sends username + encrypted timestamp to KDC on DC.

2

TGT Issued

DC verifies credentials and returns TGT + Session Key.

3

TGS Request

User presents TGT to request service-specific ticket.

4

Access Granted

Service validates TGS and grants resource access.

Key Security Feature: Passwords are not repeatedly sent across the network. The TGT acts as a "master pass" for requesting service tickets without re-authentication.
Phase 8

NetNTLM Authentication

NetNTLM is the legacy challenge-response authentication protocol kept for backward compatibility in Windows domains.

THM Question: When using NetNTLM, is the user's password transmitted over the network? Answer: Nay (No) — Only hashed challenge-response is exchanged.
💻 Client sends username
↓
🎲 Server sends random challenge
↓
🔑 Client encrypts challenge with password hash
↓
✅ DC verifies response

How It Works

  1. Client sends username + domain name
  2. Server sends a random challenge number
  3. Client encrypts challenge using stored password hash
  4. DC recomputes expected response and verifies

Security Note

Password is NEVER sent over the network. Only hashed challenge-response values are exchanged. However, NetNTLM is weaker than Kerberos and vulnerable to relay attacks.

FeatureKerberosNetNTLM
Default in ADYesNo (legacy fallback)
Authentication StyleTicket-basedChallenge-response
Password Sent Over NetworkNoNo
Security LevelStrongWeaker (relay attacks possible)

Trees & Forests

Understanding how Active Directory scales from a single domain to enterprise-wide identity infrastructure with multiple domains and namespaces.

AD Hierarchy — Forest, Trees, Domains

│    └── us.corp.local (child domain)

🏢

Domain

Basic security and administrative boundary. Contains users, computers, groups, and policies managed by a DC.

🌲

Tree

Multiple domains sharing the same namespace. Example: corp.local, uk.corp.local, us.corp.local.

🌳

Forest

Highest hierarchy level — collection of trees. The entire enterprise identity infrastructure.

RoleScope
Domain AdminControls only one domain
Enterprise AdminHighest privilege — controls entire forest
Mental Model: Domain = basic control unit. Tree = related domains under same namespace. Forest = entire enterprise identity boundary.

Trust Relationships

Trust relationships enable cross-domain authentication and resource access in multi-domain Active Directory environments.

One-Way Trust

If Domain A trusts Domain B, then users from B can access resources in A — but not vice versa.

Both domains trust each other. Users from A can access B and vice versa. Default for domains in same tree/forest.

Key Concept: Trust direction ≠ Access direction. If A trusts B, B users can access A resources (trust flows opposite to access).
